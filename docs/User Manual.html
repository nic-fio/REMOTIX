    Chapter 1

    What REMOTIX is

    1.1 · REMOTIX in short

    REMOTIX shows a full Linux desktop inside a browser tab. The Linux machine runs REMOTIX; you open its address in the browser of a laptop, a phone or a tablet, sign in with your Linux user name and password, and your desktop appears, as large as the window. There is nothing to install on the device you connect from.

    What it offers:

    • Your own desktop. Each user gets their own desktop on the machine; several people can work on the same machine at the same time, each in their own desktop.
    • The size of your window. The desktop is created as large as the browser window at the moment you sign in, up to 4096×2304.
    • Keyboard, mouse and touch. The page keeps no key combination for itself. A few (such as Alt+Tab or the Super key) may be taken first by your own computer or browser: the small ⌨ button at the bottom left of the page lists the ones that do not reach the remote desktop.
    • Sound. What the desktop plays, you hear in the browser.
    • Copy and paste. Text can be copied between your device and the remote desktop, in both directions (text only: not images or files).
    • Leave and come back. Closing the tab does not close the desktop. Sign in again, from the same device or another one, and you find your windows as you left them.
    • Encrypted. Everything travels encrypted, on one port (7447).

    1.2 · The desktops

    REMOTIX works with four desktops: GNOME, KDE Plasma, XFCE and LXQt. It uses the desktop already installed on the machine: it does not install one.

    • One desktop per machine. If a machine has more than one of the four installed, REMOTIX picks one — GNOME before KDE, XFCE before LXQt — and writes it in its log.
    • Wayland only. The remote desktop is a Wayland session. Older programs made for X11 still run, through XWayland.
    • XFCE and LXQt run on the labwc compositor, which the installation brings along as a dependency.
    • KDE Plasma runs inside a small labwc that REMOTIX starts without a screen of its own; this is what lets the desktop take the size of a new window when you come back. On AlmaLinux and RHEL 10, which have no labwc package, REMOTIX brings its own (/usr/lib/remotix/labwc).
    i
    KDE at 3K and 4K. on KDE this costs a little at very large sizes. Measured on an Intel UHD 770: no loss at 1080p and 2K; at 3K the desktop goes from 58 to 54-55 frames per second, at 4K from 58 to 44-49.

    1.3 · The browsers

    The browser needs two modern features, WebTransport and WebCodecs. These are the browsers REMOTIX declares:

    On an Android phone or tablet, use Chrome. A browser that is too old lacks these features, and the page cannot show the desktop.

    1.4 · Your session waits for you

    Your desktop belongs to you, not to the browser tab. Closing the tab, losing the network or switching device leaves it running on the machine, with every program open.

    !
    The one-hour clock. only your own input — keys, mouse, touch — counts as “touching”. A desktop left without any input for an hour is closed even if a video is playing in it.

    1.5 · What REMOTIX does not do

    What REMOTIX deliberately does not do (SPECS.md §12):

    • a Windows or macOS machine as the server: the server is Linux only;
    • an application to install on the device you connect from;
    • X11 desktop sessions (X11 programs run through XWayland);
    • file transfer, or images and files in the clipboard (text only);
    • access to the disks, printers, serial ports or smart cards of your device;
    • several monitors;
    • recording the session;
    • connections from RDP, VNC or SPICE programs.

    1.6 · The licence

    REMOTIX is free for personal use and for non-profit associations, churches and religious institutes; any other use needs a written licence from the author (remotix@nicfio.it). The source code can be read and checked, but it may not be modified or redistributed.

    The licence is in LICENSE.md, included in the installation file. People who only connect with a browser need nothing from it: it concerns whoever installs and runs the server.

    Chapter 2

    Installing the server

    2.1 · What the machine needs

    REMOTIX is installed on the Linux machine whose desktop people will use. Before starting, check these points: the installer checks them too, and stops before touching anything if one is missing.

    2.2 · The seven distributions

    REMOTIX ships one package for each of these distributions, all inside one installation file. The installer refuses any other distribution, except the derivatives named in the table.

    i
    AlmaLinux and RHEL 10. on AlmaLinux and RHEL 10 only GNOME and KDE Plasma are supported. KDE there runs inside REMOTIX's own copy of labwc 0.8.4, installed at /usr/lib/remotix/labwc (GPL-2.0; its source is published next to each release).

    Out of scope: Debian 12, Ubuntu 24.04, RHEL 9 and its rebuilds, openSUSE Leap 15; Linux Mint (Mint 22 is excluded, being based on Ubuntu 24.04, and the installation file has no package for Mint 23); distributions without systemd; immutable distributions (Silverblue, Kinoite, Aeon, Kalpa, Ubuntu Core, SteamOS).

    2.3 · The installation file

    REMOTIX is delivered as one file, remotix-X.Y.Z-R.run (X.Y.Z is the version, R the package revision). It contains the installer and the REMOTIX packages for all seven distributions; whatever else is needed comes from the distribution's own repositories, through its package manager.

    Before installing you can ask the file what it thinks of the machine. This only reads, needs no administrator rights and changes nothing:

    Checking the machine
    $ sh remotix-X.Y.Z-R.run check
REMOTIX — machine check (read only: nothing was touched)
…
The desktops:
…
Warnings and problems:
…

    The report lists the four desktops (installed or not, and whether supported), then the warnings and problems, each with a code such as RX-GPU-005. A section headed “MISSING — REMOTIX does not install it: providing it is up to the administrator:” lists what you must provide before installing — for example a supported desktop (RX-MANCA-001) or a repository (RX-MANCA-002).

    2.4 · Installing

    Copy the .run file to the machine and run it as administrator. It works like apt: it shows what it is going to do, asks once, and only then acts.

    1. Run sudo sh remotix-X.Y.Z-R.run. Without sudo it stops with “run it as administrator: sudo sh …”. The file first checks itself; if it was damaged in the download it says “the file is damaged … download it again”.
    2. The installer examines the machine (the same checks as check).
    3. It prints the plan: the steps it will take (install the packages, add people to the graphics-card groups, start the service), each marked with how it can be undone; then, under “What the package manager will do (its own simulation):”, the exact list of packages with versions, as the package manager itself worked it out; last, the port it will use (“Port: 7447 (TCP+UDP) — use --port N to change it”, or the one given with --port N). Nothing has been touched yet.
    4. If something is missing, the plan ends with the MISSING list and the line “REMOTIX is not installed: nothing was touched. Run it again when what is missing is there.”
    5. Otherwise it asks Proceed? [y/N]. Only y or yes go ahead; anything else, or just Enter, answers no and prints “Nothing was touched.”
    6. It installs, starts the remotix.service service, and checks the result: the graphics card must really encode a frame, the sign-in configuration must be complete. If a required check fails, everything it did is undone.
    7. At the end it prints the operation and its result — CONFIRMED, or CONFIRMED_WITH_CONDITIONS when something needs your attention (typically the firewall) — and reminds you about the router.
    An installation (shortened)
    $ sudo sh remotix-X.Y.Z-R.run
The plan (installation, …):
  1. …  [BEST_EFFORT]
  2. …  [EXACT]
  …
What the package manager will do (its own simulation):
  …

Port: 7447 (TCP+UDP) — use --port N to change it

Proceed? [y/N] y
…
operation …: CONFIRMED
From outside the local network: forward port 7447, TCP and UDP, on the router to this machine (REMOTIX does not do it by itself: no UPnP).

    Options you can add after the file name:

    +
    The text interface. sudo sh remotix-X.Y.Z-R.run tui runs the same installation in a text interface, with four steps (Check, Plan, Install, Ready): Enter continues, d shows details, y / n answer the question, Tab changes the port. The last screen shows the addresses to open, the certificate fingerprint and who can sign in.
    i
    Interrupted. if an installation was interrupted (power cut, closed terminal), the next run first rolls it back, so the machine is never left half installed, then starts again from the beginning.

    2.5 · Who can sign in

    People sign in with their Linux user name and password on that machine — the same ones they would use for ssh. There is no separate list of REMOTIX users.

    • root cannot sign in. The names in /etc/remotix/denied-users (one per line; it contains root) are always refused. Add other names there to keep them out.
    • Graphics-card group. To use the card, a desktop's user must be in the group that owns the render devices (usually render). The installer adds every person on the machine (or those given with --users); someone created later is added automatically the first time they connect.
    • New users need nothing else: create the account as usual, and they can sign in.
    • Wrong passwords. After 5 wrong passwords for the same user from the same network within five minutes, that user has to wait before trying again: 15 minutes the first time, then 1 hour, then 12 hours if it keeps happening (the count starts again after a day without blocks). From another network (for example the phone on mobile data) the same user can still sign in. Other users on the same network are not blocked, unless there are about a dozen errors in five minutes from that network: then the whole network waits. When only that user is blocked the page does not show the time left; the wait is 15 minutes the first time. A correct password clears the count of that user. The blocks are kept in /var/lib/remotix/ban, which REMOTIX reads only when it starts. To lift them all at once: sudo systemctl stop remotix, delete /var/lib/remotix/ban, sudo systemctl start remotix. Open desktops are not closed by the restart. The administrator can also lift the block of one address at once with the UNBLOCK command, if the server was started with its command socket.
    • One desktop per user. Someone signed in at the machine itself (in front of its screen) cannot open a REMOTIX session at the same time.

    2.6 · Firewall and port

    REMOTIX uses one port, 7447, on both TCP (the page) and UDP (the desktop itself). The installer does not change the firewall: if one is on, it says so in the plan and at the end, and you open the port yourself.

    With another port (--port N), open that port, TCP and UDP, instead of the service or profile.

    From outside your home or office network, the router must also forward the port, TCP and UDP, to the machine. REMOTIX does not do this itself (no UPnP).

    2.7 · The certificate

    The connection is encrypted with a certificate. At its first start REMOTIX makes its own, valid for 365 days, in /var/lib/remotix/certificates. Browsers do not know it, so the first time a device connects the browser shows a warning (2.8 “The first connection”).

    • The name in the certificate is the machine's name. If people connect with the IP address instead, write it in a file of /etc/remotix/remotix.conf.d/, for example REMOTIX_OPTIONS=--name 192.168.1.10, and restart the service with sudo systemctl restart remotix. A name that does not match makes the browser show a different, harder warning.
    • When it expires, REMOTIX makes a new one, and browsers show the warning once more.
    • A real certificate: whoever has a domain name can use their own. Put the certificate (PEM, the full chain may follow it in the same file) in page.pem and its private key (PEM) in page.key, in /var/lib/remotix/certificates, and delete page.ours: that file marks a certificate REMOTIX made itself, which it replaces when it expires. Restart the service. A certificate without that mark is used as it is and never replaced, not even when it expires — renewing it is up to you. If the key does not match the certificate, the service does not start and its log says so.

    2.8 · The first connection

    Once the service runs, anyone with an account can connect from a browser.

    1. Open https://<machine>:7447 — the machine's name or address, and the port.
    2. The first time on each device, the browser warns that the connection is not private or the certificate is not trusted. This is expected: open the details and choose to continue to the site. The browser remembers the choice.
    3. The page “Sign in” appears. Type your Username and Password on the server and press Connect.
    4. Your desktop appears, as large as the window. If the window changes size later, the picture is scaled; the desktop takes the new size the next time you sign in.
    5. To finish, choose “Log Out…” in the desktop's own menu. Just closing the tab leaves the desktop running (1.4 “Your session waits for you”).
    Chapter 3

    Looking after an installation

    3.1 · Checking an installation

    The installer stays on the machine as remotix-install, so the installation can be checked again at any time, without the .run file.

    Checking an installation (shortened)
    $ sudo remotix-install status
…  CONFIRMED

Certification of installation …: GREEN
  PASS     …

    It lists the installer's operations, then repeats the checks made at installation time and gives one of three results:

    On a machine where REMOTIX was not installed by the installer it says “REMOTIX is not installed by the installer on this machine.”

    3.2 · Updating

    To update, run the newer .run file exactly as for the installation. There is no automatic update.

    1. Copy the new file to the machine and run sudo sh remotix-X.Y.Z-R.run.
    2. The installer sees the existing installation and makes an upgrade plan: only the packages change.
    3. Answer y to Proceed? [y/N].

    The service restarts, and open desktops are not closed: people connected at that moment see the page disconnect, sign in again and find their windows. If the version is already installed the installer says “REMOTIX X is already installed: nothing to do.”

    Updates of the distribution itself (apt upgrade, dnf upgrade and so on) are fine: the installation stays valid.

    3.3 · Uninstalling

    REMOTIX is removed with the installer that stays on the machine:

    Uninstalling (shortened)
    $ sudo remotix-install uninstall
The plan (uninstallation, …):
  …

Remove REMOTIX? [y/N]

    Like the installation, it first shows the plan and asks Remove REMOTIX? [y/N]. It undoes what the installation did, and only that:

    • it stops and disables the service;
    • it closes every open REMOTIX desktop — unsaved work in them is lost, so warn people first; a session at the machine itself or by ssh is not touched;
    • it takes people out of the render group that REMOTIX put them in, and removes the access REMOTIX gave to the render devices;
    • it removes each user's ~/.local/state/remotix/session.log;
    • it removes the packages it installed. A package that something else now needs is kept, and the plan says so.
    !
    Known limit. packages added later by an upgrade (a new dependency of a newer version) are not removed by uninstall.

    3.4 · On a shared machine

    On a machine that many people share, no ordinary user may take it down for everyone. REMOTIX installs one rule for that, and leaves one more to the administrator.

    Installed by REMOTIX: /usr/share/polkit-1/rules.d/50-remotix-no-poweroff.rules. With it, ordinary users can no longer power off, restart, suspend or hibernate the machine — from a REMOTIX session or sitting at it, also with other people signed in. Without it, anyone connected could power the machine off without a password. Administrators still can, with sudo systemctl poweroff and sudo systemctl reboot. The installation plan says so before it asks; uninstalling REMOTIX removes it.

    The administrator's choice: one more ready-made rule, switched off, in /usr/share/remotix/belts/. Nothing reads it there; it works only once the administrator copies it into place.

    !
    Whose choice. switching it on is the administrator's choice, and uninstalling REMOTIX does not remove a file the administrator copied: remove it with the command in the last column.

    Chapter 4

    Glossary

    4.1 · Words used in this manual

    Browser
    The program you use to open web pages: Chrome, Edge, Firefox.
    Certificate
    The machine's proof of identity for the encrypted connection. REMOTIX makes its own; browsers do not know it and warn once per device.
    Desktop
    The screen with windows, menus and programs: GNOME, KDE Plasma, XFCE or LXQt.
    Distribution
    A version of Linux: Debian, Ubuntu, Fedora, AlmaLinux, Arch, openSUSE.
    Firewall
    The part of the machine that decides which connections may come in. Port 7447 must be open in it.
    Graphics card
    The chip that draws the screen. REMOTIX uses it to compress the picture.
    labwc
    A small Wayland compositor. XFCE and LXQt run on it; KDE Plasma runs inside it under REMOTIX.
    Log
    The file or journal where a program writes what it does and why it failed.
    Port
    A numbered door of the machine for network connections. REMOTIX uses 7447, TCP and UDP.
    .run file
    The single installation file of REMOTIX, run with sudo sh.
    Session
    Your desktop with its open programs. It stays alive when you close the tab, and ends when you log out or after an hour without input.
    Wayland
    The modern way Linux desktops draw on the screen. REMOTIX desktops are Wayland sessions.
